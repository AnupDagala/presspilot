# Deployment and recovery runbook

## Local recovery

Use `docker compose stop` to stop containers while preserving both business and Temporal volumes. Use `docker compose up -d` to restart. Do not use volume deletion as a routine reset. The native scripts record process IDs and start times; `stop-local.ps1` stops only matching processes and preserves state. A sandbox session expires after one hour; create another for a clean demonstration rather than changing historical audit records.

A worker restart replays durable history and resumes the approval wait. It does not reissue recorded model activities or committed mutations. If the API dies after a commit but before replying, retry the same exact request key/arguments or inspect the stored execution. Different arguments using an old key fail. If provider delivery is ambiguous, keep the token reservation charged and escalate; do not claim or force exactly-once external inference.

The API dispatcher's stable workflow IDs reconcile outbox starts. Database availability failures leave requests retryable. Production eligibility failure invalidates a proposal. Permanent activity errors and exhausted retries escalate. Inspect Temporal histories for a failed escalation activity when the underlying organization/session has expired or authorization is revoked; expiry does not permit bypassing the backend. Pending approval expiry is also reconciled by the API dispatcher.

## GCP preparation — not applied

`terraform init -backend=false` and `terraform validate` are local preparation. They were completed without cloud provisioning. Applying this configuration creates paid infrastructure and requires explicit authorization, a chosen GCP project/region, deployer IAM, image registry, Temporal Cloud namespace and secrets. The configuration defaults to private services and disables public sandbox and live model calls. It never binds `allUsers`.

1. Choose region and image digests; build API/web/worker images from the monorepo root with the provided Dockerfiles. Run the Compose integration/browser/evaluation checks in a Docker-capable host before promotion. Docker execution has not been verified on the current machine.
2. Configure a protected remote Terraform state backend. The checked-in lockfile pins the Google provider. Review `terraform plan` before any authorized apply; no plan or apply was performed here.
3. Provision foundation resources only: enabled APIs, service accounts, Cloud SQL and secret containers. Populate secret versions from protected files, not command-line values or Terraform variables. Provision the application database user separately with the necessary migration/runtime privileges. No password resource is managed by Terraform.
4. `presspilot-database-url` uses the Cloud SQL Unix socket under `/cloudsql/<connection-name>` with appropriately encoded credentials, database `presspilot` and connector-provided transport. `presspilot-worker-secret` is a high-entropy service token. `presspilot-temporal-key` is an API key for the supplied namespace. Set Temporal TLS and namespace/address from its actual connection details.
5. Run the API image once as an authenticated Cloud Run migration job with the database connection volume and `MIGRATE_ONLY=true`. The embedded bootstrap migration is idempotent. Application deployments set `AUTO_MIGRATE=false`. Future schema changes need numbered forward migrations and expand/contract compatibility; avoid editing deployed schema history casually.
6. Deploy the private API, web gateway and worker pool after secret versions and schema exist. The web/worker service accounts receive only API invocation. The worker has no database connection secret. API access requires Cloud Run service authentication plus application session/tool authorization. Server-side gateway/worker requests use `X-Serverless-Authorization` for Cloud Run identity while retaining the application worker bearer token separately.
7. Provision private organization memberships and sessions through an authorized operator workflow. Do not enable sandbox role switching for private records. Configure an approved identity/onboarding integration before broader operational use; the current private session provisioning is deliberately small.
8. Verify health checks, worker polling logs, dispatcher progress, one bounded test case, stale approval invalidation, and backup/restore. A successful worker-pool deployment is not sufficient evidence that it is polling. Google explicitly notes this [runtime verification requirement](https://docs.cloud.google.com/run/docs/deploy-worker-pools).

The worker pool allocates one continuous instance and does not autoscale. The API dispatcher uses one minimum instance with CPU idle disabled. The web service can scale to zero and is capped at two instances. These are deliberate execution constraints; long-lived work is not attached to a transient HTTP response. [Service authentication](https://docs.cloud.google.com/run/docs/authenticating/service-to-service) and [Temporal API keys](https://docs.temporal.io/cloud/api-keys) were checked against official guidance.

## Costs and application limits

Persistent costs include Cloud SQL instance/storage/backups, the continuously allocated API CPU/memory, one worker-pool instance, Temporal Cloud namespace/storage/actions, image storage, logs and egress. Shared-core Cloud SQL (`db-f1-micro`, PostgreSQL 18, 10 GiB, zonal) is a demo-oriented configuration with no high-availability claim. The always-on worker/API means an idle deployment is not free.

Estimate monthly infrastructure as regional unit rates × allocated CPU/memory hours (approximately 730 per continuously allocated instance), plus database/storage/backup and Temporal usage. Obtain an actual quote from current [Cloud Run pricing](https://cloud.google.com/run/pricing), [Cloud SQL pricing](https://cloud.google.com/sql/pricing) and the selected Temporal plan. No numeric monthly price has been invented or measured. Cloud budget alerts notify rather than enforce a hard account spending cap.

Live provider calls require server-only configuration, persisted per-case token/turn reservations, a daily organization call/token cap, 1,024 output tokens per request and at most two concurrent activities. Default daily limits are twenty calls and 100,000 tokens; configure limits to an explicitly approved budget and use provider-account hard limits where supported. Provider model pricing is an operator-supplied assumption, not inferred from mocked usage. See `PROVIDERS.md` for the network and delivery limits.

## Backup, restore and rollback

- Local backup: run `pg_dump -Fc` against a protected connection configuration or `PGPASSFILE`, writing an access-restricted backup outside source. Keep credential values out of command arguments. Preserve the Temporal database/volume independently; quiesce the dev server before file-copy backup.
- Cloud: Cloud SQL backups and point-in-time recovery are enabled with deletion protection. Restore to a separate instance first, verify migrations, tenant isolation, orders, proposals, approvals, unique executions and audit sequences. Never blindly replay approved actions after a database restore.
- Cross-system recovery: compare restored business execution records with Temporal histories. If an activity appears completed in history but its database state was rolled back by restore, freeze affected cases and reconcile with a person. A workflow replay alone cannot repair inconsistent independent backups safely.
- API/web rollback: route traffic to the previously tested image revision. Database changes must remain compatible with both revisions; prefer expand/contract migrations.
- Worker rollback: use a replay-compatible workflow build. Before changing workflow branches/timers, add Temporal versioning/patch markers and replay historical workflows. The supplied single workflow build was restart-tested; multi-version rollout is not yet implemented.
- Secret rotation: update Secret Manager versions, roll API/worker credentials together or implement overlapping acceptance before rotating a live installation. The current gateway supports one worker secret, so rotation needs a controlled restart window.

## Monitoring

If the original requester loses authorization, worker tools remain denied. A currently authorized administrator can select **Request administrator review** on an active case. This server-authorized operation withdraws pending proposals, records an audit event and escalates the case without changing the order. Reauthorize or resolve the underlying request through a person; an old approval cannot execute after escalation. Automatic approval review rejected an attempted worker authorization exception, so no such exception is present.

Go emits JSON request logs with request/trace/span IDs, method/path and measured duration; it does not log bodies, headers or secrets. OpenTelemetry creates bounded HTTP server spans, propagates W3C trace context, records status and sanitizes route names. `OTEL_MODE=console` exports local spans; `off` disables export. GCP configuration sets `OTEL_MODE=gcp` and `GCP_PROJECT`, uses ADC, the fixed Telemetry OTLP gRPC endpoint, a 10% sampler, a 256-span queue and five-second export timeout. Terraform enables the Telemetry/Trace APIs and grants only trace-write and quota-use permissions to the API identity. This follows [Google's in-process OTLP export guidance](https://docs.cloud.google.com/stackdriver/docs/instrumentation/migrate-to-otlp-endpoints). Local export and secret omission are tested; cloud delivery is unverified. Full tracing through worker/provider activities remains an extension.

Temporal records workflow/activity histories. Worker readiness has a small health endpoint. Terraform supplies API error metrics/alerts with configurable notification channels. Configure channels before expecting notification delivery. Track queue age, dispatch failures, Temporal poller availability, escalation rate, invalidation rate, provider reservations and Cloud SQL health. Verified alert delivery remains pending deployment access.
