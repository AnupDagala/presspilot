# Security and focused threat model

Report suspected issues privately to the repository owner. No public bug-report endpoint or email address has been invented.

## Assets and trust boundaries

Business state, proposal/approval bindings, organization membership, audit evidence, session tokens, worker credentials and provider secrets are protected assets. The browser and customer messages are untrusted. Provider output is untrusted. Retrieved documents are evidence, not instructions. The Go backend is the enforcement boundary. PostgreSQL is authoritative. Temporal activities are authenticated callers of a narrow gateway.

| Threat                                  | Implemented control                                                                                                                                                                 | Residual limit                                                                                                         |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Cross-organization access               | Tenant keys on every lookup; composite foreign keys; membership from hashed server session; tested foreign-case/proposal rejection                                                  | No PostgreSQL RLS layer; review tenant filters in every new query                                                      |
| Operator approves action                | Roles are read from active membership in the database; server rejects operator approvals                                                                                            | Sandbox role switching is intentionally allowed only inside isolated seeded organizations                              |
| Stale or substituted approval           | Canonical digest binds org/order/case, order/policy versions, exact arguments and evidence; approval stores digest, approver and expiry; executor recomputes under transaction lock | A changed policy can require a fresh approval even when meaning is equivalent                                          |
| Concurrent or repeated effects          | Organization transaction lock; conditional order version/state update; unique execution per proposal and case; request argument digest                                              | Organization-wide serialization trades throughput for correctness                                                      |
| Customer prompt injection               | Tool name/argument allowlist; no model execution tool, SQL, shell or arbitrary network tool; deterministic eligibility and authorization                                            | A model may produce poor explanations; never an action permission                                                      |
| Provider SSRF / credential exfiltration | Exact approved HTTPS URLs; DNS private-address rejection; no redirects; secret stays in server HTTP headers                                                                         | Fixed reputable destinations reduce rebinding risk; deployment egress firewall is an additional recommended control    |
| CSRF / token theft                      | HttpOnly SameSite Strict cookies, secure flag in cloud, exact-origin checks, same-origin gateway, CSP; session expiry; tokens stored as digests                                     | Private session provisioning is an operator workflow, not a complete enterprise login system                           |
| Provider/compute spend                  | Disabled live sandbox; persisted token/call reservations; bounded tools, turns, outputs, activity retries, worker concurrency, duration; daily org limits                           | Operator-supplied pricing bounds must match the configured model; no provider billing reconciliation has been verified |
| Webhook spoof/replay                    | HMAC over raw body; fixed approved shop; durable unique event identity before ack; different-content identity rejected                                                              | Production printing state is not derived from Shopify fulfillment state                                                |
| Secrets in artifacts                    | Ignored runtime files; no body/header/credential logging; source scanner; no browser network traces                                                                                 | Use platform secret storage and restrict permissions of local runtime files                                            |

Runtime defaults: eight model turns, sixteen business tools, 12,000 tokens per case (maximum configurable 20,000), three activity attempts, two concurrent activity tasks, four workflow tasks, ten-minute approval window (maximum one hour), three reassessments, one-hour sandbox expiry, twenty sandbox cases and one hundred concurrent sandbox organizations. Model records contain tool requests, concise decision summaries, exact configuration and observed usage. No private chain-of-thought is requested or persisted.

Production deployment requires review of IAM, organization onboarding, identity lifecycle, data retention, secret rotation, pricing, test-store permissions and monitoring. This repository does not claim production security certification.
